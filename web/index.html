TAG design review impact

How long W3C TAG design reviews take, and how much they changed the features they reviewed. Latency comes from GitHub structure; impact labels come from a model reading each thread, so spot-check them: every number links to the reviews behind it.

Review latency

TAG time is open-to-close time minus time waiting on the requesters: while a pending external feedback or pending editor update label was on the issue, or between a TAG comment and the requester side's reply. See docs/latency.md.

Design impact

A model reads each review thread and labels it against a fixed taxonomy. The headline, TAG impact, asks whether the design changed after the TAG's first substantive feedback and whether the thread credits the TAG for that change. A change counts as TAG-caused when the requester ties it to TAG feedback (explicit), when it follows a specific TAG ask with no other cause named (implicit), or when the TAG is credited alongside others such as the working group or other implementers (shared). Changes the thread credits only to others, or gives no reason for, are counted as changed, not credited. The size of a credited change runs from documentation (explainer, questionnaire or considerations text) and cosmetic (renames, ergonomics) through functional (behaviour or exposure changes such as an added permission or mitigation) to significant (a different architecture). A proposal abandoned with the TAG credited counts as blocked.

The other dimensions describe the change and the review: the kind of change (naming, API shape, privacy or security, scope cut, architecture, documentation, venue or process), where it landed (explainer, spec text, implementation, an issue filed, or only promised), and the TAG's final verdict. Hover a value for its definition. The taxonomy came from a stronger model reading 30 diverse threads, then refined by hand; see docs/taxonomy.md.
